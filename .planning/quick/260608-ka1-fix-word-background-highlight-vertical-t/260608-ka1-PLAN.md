# Quick 260608-ka1 — Word-background highlight: vertical padding >> horizontal

## Problem (user, live UAT of 260607-uzv-05 box-shadow fix)

1. The per-word highlight background's top/bottom padding is visibly **larger**
   than its left/right padding (not "parejo").
2. Increasing the highlight size (padding slider) grows the box **much more
   vertically** than horizontally.

## Root cause (DOM-measured, Studio Player scale 0.31)

The background span is `display:inline-block` and inherits the caption's
`line-height` (config Interlínea = **1.3**). An inline box's height = line-height
(`1.3 × 60 = 78px`), but its width hugs the glyph advance. The glyph ink is only
~46–57px tall. So:

| | composition px |
|---|---|
| bg border-box height | 78 (line-height) |
| glyph ink height | 46 ("diaria.") – 57 ("palabras") |
| vertical padding / side | **19** |
| horizontal padding / side | **3** |
| ratio vertical / horizontal | **6.3×** |

The `box-shadow` spread (the padding control) is uniform on all 4 sides, so the
delta is constant; the imbalance is entirely the line-height leading inflating
the vertical box. Complaint #2 (grows more vertically): horizontal band growth
collides with neighbor words (gets visually covered) while vertical grows free.

## Fix

Add `lineHeight: 0.95` to `getWordBackgroundStyle`'s returned style (applied only
to the active word's bg span). This shrinks the bg box to ≈ the font em, hugging
the glyph vertically so vertical padding ≈ horizontal.

`0.95` chosen by live measurement: makes the tallest words (ink 57 + 5px stroke =
62) exactly even (3px/side) AND fully covered (colored height 63 ≥ 62); box 57 ≥
fill ink 57 means no clipping even at padding 0. Reduces short-word vertical
excess 19 → ~8.5px (the residual is the font's baseline descent reservation,
inherent without `text-box-trim`, which is not safe across preview/render Chrome).

No horizontal-layout change (line-height only affects the box height, glyph stays
baseline-anchored → no shift on activation, neighbors unaffected).
